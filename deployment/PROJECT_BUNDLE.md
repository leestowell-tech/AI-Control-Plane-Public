## Purpose before transport

Recover the intended use from the conversation before choosing a route; do not make the person repeat settled choices. These are distinct purposes, not a fixed product ladder:
- **Use methods now**, including on a borrowed account: read the methods and apply them to the task. Session use needs no personal-memory setup. Do not import the visitor’s private context, bind the account holder’s state to the visitor, or claim personal continuity. Anything entered in that account may remain with its holder.
- **Recover my own continuity away from my usual device**: methods access is not private-context access. Verify the authorized identity and suitable private context route before retrieving personal state. A borrowed account is not permission to disclose that state. If no safe route is established, continue methods-only and identify the precise missing gate.
- **Leave methods for someone else / create their owned copy**: keep the original read-only, use a methods-only artifact, and let the recipient choose scope. Delivery alone does not install anything or authorize state capture.
- **Install or update ongoing operation**: use recipient-owned methods and verified recipient-private memory; preserve their preferences and history. A separate private repository/copy is not a public GitHub fork. Account settings, connectors and permissions require their own authorization.

Use the simplest supported transport for the selected purpose. ZIP extraction is host-dependent; a sectioned Markdown kit is an alternative, not proof of actual host support. Full installation and service offerings remain possible without making them prerequisites to immediate useful work.

## Project instruction
Use the uploaded AI Control Plane files as portable method instructions for this Project, subject to host instructions and the recipient’s current authority. Boot from `BOOT.md`; use `OPERATOR.md` as the user-facing surface; load deeper kernel files only when triggered by the task. Exact command wording is not required. Never claim durable persistence unless an actual writable destination was updated and verified.

For ongoing personal memory, the installer must also bind the user's own state destination and install the rendered ACCOUNT_INSTRUCTIONS or PROJECT_INSTRUCTIONS template in the user-selected account-wide or Project settings. The files and empty template alone do not supply that binding. Follow `deployment/UPDATE_EXISTING_INSTALL.md` when a previous snapshot has already been delivered; do not assume an upload updates itself from GitHub.

## Runtime rules
- Kernel authority, user-instance state, and domain authority remain separate.
- Conversation history is not durable/current-state authority.
- Capture only into the recipient-owned verified private copy/store with actual write authority and receiver readback. A writable file alone, public fork or upstream directory is insufficient.
- If no durable write path exists, emit a typed `PERSISTENCE HANDOFF` instead of claiming capture succeeded.
- If uploaded files become stale relative to the canonical GitHub kernel, state that currentness is unverified and request/update from the canonical source when possible.

## Acceptance test
Respect an owner-selected ordinary-use feedback interval. The following cases specify evidence for a claim, not mandatory supervised homework. See `tests/PROTOCOL_ACCEPTANCE.md` for the full profile.
1. Open a fresh Project chat.
2. Ask `help`, `instructions` or `what are the commands again?`; receive only the short start menu. Then ask `all commands` for the full reference or ask about one name.
3. Ask `what's active?` and confirm it distinguishes missing user state from invented state.
4. Run one disposable `capture this` test and verify a real write receipt or typed fallback.
5. Start a second fresh chat and test `reset`/recovery.
