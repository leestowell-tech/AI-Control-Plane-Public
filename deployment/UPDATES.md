# Source-to-instance updates

Status: CURRENT TASK-TIME WORKFLOW / NOT AN UNATTENDED UPDATE SERVICE

## Owners and records
The shared maintainer owns the portable release and source provenance. The user owns instance data, preferences, domains and effect authority. The active assistant handles comparison and receiving within its grant. Use the user's existing current-state binding for inspected/accepted release and unresolved compatibility; no parallel registry is required.
Read deployment/RELEASE.md and deployment/CAPABILITY_PROFILE.json on the first relevant boot/reset or after a material source change. Read only the current release summary when unchanged, then load relevant methods selectively.

## Compare before applying
1. Recover the instance's installed instruction text/version if known, accepted source version if recorded, current release, actual dependency/tool changes and prior rollback point. Unknown installed settings are unknown; repository publication does not update them.
2. Compare material changes for purpose, authority, privacy, resource, domain and host compatibility. References to current sources do not authorize blindly adopting future semantics. Do not import another user's grants or personal preferences.
3. Source corrections and compatible procedure improvements may be used within valid current authority. Changes to new tools, access, charges, unattended effects, governing authority or data custody require the specific user decision. Keep unrelated valid methods usable if one change is held.
4. For applicable updates, inspect the required source closure and meaningful invariants, update only the actual affected entry/state within authority, preserve unrelated settings and records, publish with revision checks and read back. If account settings cannot be changed here, prepare one complete minimal paste action; do not claim installation.
5. Record available source, inspected source, actually adopted change, receiving evidence and unresolved host/behavior separately in the instance. A short description plus source version and rollback point is sufficient; do not log every unchanged boot.
6. Revalidate the affected behavior after significant change. Respect owner-selected normal-use feedback rather than inventing a supervised trial. Source/structure checks remain distinct from fresh-chat and ordinary-use evidence.

## Shared source evolution
A maintainer adapting an upstream method reviews its real status, evidence, currentness and private/source-specific dependencies. Preserve candidate/pilot labels, remove private instance detail, and make runtime references self-contained in the portable repo. Update the method, route/profile, templates, affected prepared entries, source provenance and package together.
Retain the editable production recipe, stable source identities and manual-edit boundaries. Pin the actual source snapshot and make manifest/profile/release identity agree before delivering a rebuilt package. Recheck affected dependency closure and actual candidate bytes; a refreshed hash does not by itself establish applicability, safe content or provenance. Instance-state sources are never part of a shared package, including aliases into them. Template seeds remain separate. Rebuild affected outputs rather than assuming the previous attachment or installed entry changed itself.
Capture a material missing capability or incompatible change in the owning mission. Share only consented generalized feedback; a user's memory is not an automatic training/feed export.

## Rollback and exit
Retain a previous compatible source/version. Revert only the affected method/entry; never roll memory backward wholesale. Reconcile external effects separately—configuration rollback does not undo them.
If the maintainer is unavailable, preserve usable local/exported sources, exact bindings and an ordinary operator help/reset path. For the installed owned-copy route, retain the recipient's verified private copy/store and keep the original methods read-only. Methods and state may coexist in that recipient-owned private repository; they must not be conflated with a directory in a public/shared upstream. An ordinary public fork is not private storage. Verify actual provider owner/access before capture; unknown access requires a handoff. This does not authorize creating repositories, changing visibility or migrating existing state.

## Current limits
A mutable repository can make a newer source visible on a later read. Visibility is not admission, successful loading or observed benefit. Task-time checks cannot act while no session is running. A future unattended update/delivery requirement needs an actual separately authorized trigger/receiver under kernel/MAINTENANCE.md.
