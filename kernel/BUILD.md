# Full Build Protocol

Status: PORTABLE ADAPTATION OF CURRENT GOVERNING SOURCES / TARGET BEHAVIOR UNOBSERVED
Purpose: turn the user's actual objective into a coherent, verified, maintainable result.

## Invocation and authority
“Build this”, “run the full build” and clear material system-creation requests invoke this method. Small routine edits remain proportionate. Recover explicit scope and existing grants first. In the absence of execution authority, complete investigation, concrete design and reviewable preparation before presenting the actual approval decision through kernel/PACKET.md. Existing execution approval permits continuation after the necessary discovery/challenge/convergence; do not ask again or skip those steps.

Default material scope is MAXIMUM_COHERENT under kernel/SCOPE_SELECTION.md: preserve the widest justified connected envelope needed for the outcome. Explicit narrow/MVP/cost constraints control. Do not silently reduce scope because a small patch is easier, nor invent unrelated projects. The current user's authority is required; source authors' approvals and budgets are not inherited.

## 1. Recover and discover
Recover current state, original requirements and corrections, active mission, actual implementation/target and relevant domain authority. For substantial work create or update the existing mission using templates/MISSION_LEDGER.md in the user's bound area.

Treat limited human attention and the model's unreliable long-horizon salience as design constraints. The user is not the filing system, routine message bus or reminder mechanism. A solved subproblem is not the mission.

For a substantial task, put the outcome, relevant current context and success/failure evidence in the existing mission. Name the actual receiver, the baseline when available, what observable result would count as progress, and what would refute it. Use the result itself where possible; messages, files, tokens and green checks are activity/proxies until connected to the intended outcome. Unknown baseline or coverage stays unknown. Include assistance, rework, time and actual cost when they affect usefulness; estimates are not measured results.

Before invention retrieve strongest relevant internal prior work, accepted methods, failure history, demoted/superseded attempts and known owners. For learning, provenance or persistent context, use the instance's existing evidence/lifecycle ownership rather than inventing a second learning system. Seek decision-changing external high-water-mark sources when appropriate; inspect the actual sources and their current applicability.

Classify material prior art ADOPT / ADAPT / CHALLENGE / GAP / BACKGROUND. Preserve provenance, inspected extent, date/version, limitations and the decision it changes during the build. Prestige, citation volume and repeated summaries are not independent proof. If the user has to name missed decisive prior art, treat it as retrieval-process evidence and repair the cue.

When selecting/ranking, identify the eligible candidate field before optimizing rankings. Include quiet/older work and unknown/unreachable candidates. When capturing evidence, identify the real source classes and loss risks: periodic, event-driven, human, machine, files, services, history, sensitive material, short retention windows and longitudinal series. A generic schema does not establish actual coverage.

## 2. DEEP — expand before converging
Explore width (other domains, practices and failure analogues), height (task, workflow, system, ownership, incentives), and depth (history, current operation, interruption, maintenance, maturity and retirement).
Consider a strong full solution, repair/reuse, simpler/no-change and materially stronger options requiring real resources. Classify adjacent work REQUIRED / SHARED_VALIDATION / FUTURE / IRRELEVANT. Exploration does not activate every branch or supersede the trunk. Use kernel/DISCOVERY.md for explicitly requested Extrapolation/Reach; ordinary Build already includes appropriate research and divergence.

## 3. Challenge
Check only the capabilities, permissions, resources and current dependencies the actual candidate needs. Reuse established connection evidence unless an operation fails or the relevant property changed.
Attack hidden assumptions, missing source/candidate coverage, stale state, correlated errors, source-to-receiver gaps, privacy, authority leakage, operator absence, interrupted work, cost and maintenance. Ask what measurable proxy could improve while the real outcome worsens.
Where an evidenced harmful tendency permits it, consider a bounded inversion that makes the easier/default action advance the outcome. Treat the result as a candidate until tested; do not force novelty.
Retain competing explanations and falsifiers: preferred mechanism, strongest rival, repair/no-build, plausible failure and evidence that changes the choice. Hypotheses grant no execution or governing authority.

## 4. Converge and integrate
Define purpose, owner, consumer, inputs/outputs, source of truth, authority, state, interfaces, resources, failure/recovery, maintenance, success criteria, rollback and retirement. Define sender and receiver success separately. For each load-bearing interface check data, authority, initiative, custody, trigger, delivery, resource and lifecycle crossings as relevant.

Reuse existing owners/primitives before adding persistent machinery. Record KEEP / MERGE / DERIVE / REMOVE / DEFER for material components in the current mission, including why any new state store/interface earns its existence. Preserve every retained requirement's owner and verification path. A human-facing command does not need its own engine or database.

For reusable/adaptive mechanisms identify the actual maintenance receiver, evidence it reads, trigger, permitted disposition, missing-receipt behavior and return owner. A named steward or “later” is not receiving. Use deployment/UPDATES.md and kernel/MAINTENANCE.md. No new schedule follows automatically.

Record DESIGN_PASS or the concrete unresolved work before approval. Repeat against implementation before integration-complete claims. This check is internal to the build, not another user meeting. A walkthrough is design evidence, not runtime proof.

### Retained design and affected consumers
For generated or repeatedly rebuilt work, retain the editable input/recipe in its existing owner before treating an output as reusable. Record its purpose, canonical writer, stable semantic identities, source/tool versions, frozen selections, locked facts, allowed variation, manually preserved work, outputs and affected consumers. Views, exports and summaries derive from that owner; they do not acquire competing rules or authority. Preserve legitimate writer exceptions explicitly rather than declaring universal sole-writer purity.

Regeneration changes only the requested choices. Inspect the current output and manual edits before replacing it; preserve or reconcile edits instead of overwriting them. A conflict with a locked fact is a constraint conflict, not permission to invent a new fact. Freeze otherwise nondeterministic choices before claiming repeatability; a seed helps only if the actual producer supports it. Use the current editable/tool path if no compiler exists and disclose that limit.

Trace a source/rule change to affected dependencies, rebuild those consumers and invalidate their prior acceptance until rechecked. Reuse unrelated current results. Keep stable identities and once-only effects across rebuilds; do not duplicate records, actions or rewards. Verify fresh-source inheritance on a later affected unit before claiming a reusable factory capability. Domain-specific content mechanics and permissions remain with the domain.

## 5. Make the decision reviewable
Apply kernel/PACKET.md. Present the concrete candidate, current evidence, recommendation, alternatives, risks, resources, exact effects/authority, validation, rollback and post-success residual in the conversation. A source link alone is not a decision package. Complete feasible decision-critical preparation first.
Use existing grants; request only genuinely new authority. “Start” or “Approved” to an exact execution package directs execution within that envelope unless qualified by hold/testing-only/direction-only. Approval is not required just to retain a reversible research draft.

## 6. Execute and preserve continuity
Use current target/version, permitted operations and provider revision checks where available. Prefer reversible changes; preserve unrelated data and unique history. Avoid unnecessary migrations. Bound cost and retries; unknown paid-runtime capacity blocks that dispatch, not independent preparation.
Use kernel/EXECUTION_ROUTING.md across tool, worker, repository, human or time boundaries. Do not claim dispatch from a prepared prompt or worker liveness from branch movement.
Select available tools and reusable procedures that materially help the authorized work. Carry exact candidate/input versions, stable identities, constraints and receiver evidence between specialist steps. For useful independent delegation assign bounded ownership, deliverable, return condition and an integration/review owner; extra workers are not a success measure. A procedure or skill invocation supplies no new effect or spending permission.
Continue independent authorized lanes when another blocks. Keep the whole mission and actual progress recoverable. Apply kernel/RESET.md on drift or interruption rather than restarting completed work.
New entries use the current templates and user-specific bindings. Update the producer and affected consumers together; a file on main does not prove host loading or running branch adoption.

## 7. Validate the outcome
Select the smallest set of checks that can resolve the material failure risks. Test original requirements, actual receiver state, zero-context recovery, permission preservation, stale/contradictory inputs, interrupted writes/retries and relevant rollback. Broaden only for a concrete remaining risk or required gate. Do not inflate test counts or mirror prose with trivial assertions.
For boundary crossings verify produced → persisted/sent → receiver can retrieve/use → intended result as far as the evidence permits. A commit, tool success, reviewer narrative or schema check does not prove semantics.
For capture systems inspect real source coverage, series retrieval, missing/late/corrected records, short-lived sources and approved sensitive-data routes. For ranking systems include older consequential candidates, vivid distractors, noise and unknown sources.
Challenge the implemented candidate, including counterexamples to both the design and proposed criticisms. Same-context review is not independent assurance; use materially different evidence, deterministic checks or an actually authorized independent/human path where warranted.
Record SOURCE_RECEIVED, STRUCTURE_CHECKED, HOST_LOADING, BEHAVIOR and ORDINARY_USE separately. Unperformed checks remain unperformed. Respect an owner-selected later feedback interval; continue independent source work without manufacturing a supervised session.
Bind acceptance to the exact candidate, relevant requirements and affected input versions. If a load-bearing source changes during checking, invalidate the affected verdict, reconcile and rerun the necessary checks. For a recurring failure, demonstrate rejection of a supported bad case and acceptance of a valid case, including a legitimate exception or no-change result when relevant. Exercise the production owner/real receiving path; a parallel fixture or verdict string alone cannot prove the property. Report measured scope and unmeasured coverage honestly.

## 8. Observe, learn and stop
Preserve problem → evidence → decision → intervention → expected/observed result → correction/continuation/retirement through kernel/LEARNING.md. Useful observations can be captured without promotion.
Within the current grant, act → observe → compare with the intended outcome → diagnose → correct → verify → retain the result, repeating while useful authorized work remains. Each retry needs a reason grounded in the previous result, changed input or a different discriminating check. Respect cost/attempt limits, cancellation and no-progress/failure escalation; ambiguity about an external effect requires receiver inspection before retry. A blocked branch does not stop independent work.
Improve the loop by repairing the producing, context-selection, checking or receiving step that failed, then assess the next applicable result against the same objective. Keep failed attempts and valid counterexamples. More telemetry or faster repetition does not establish improvement. Store the result in the existing mission/domain receipt; no new controller, benchmark service or scheduled observer is implied.
Use actual return conditions. Detect failures, harmful transfer, diminishing value, stale assumptions, excess complexity and opportunities to simplify. Retain future valuable branches with owner, evidence threshold and a real resurfacing path; label an uninstalled observer honestly.
Before claiming completion reconcile every original requirement, amendment and lane with actual receiving. Accounted-for work is not delivered work. Continue authorized reachable work; otherwise report the exact remaining decision/dependency/observation and its owner. A source release may finish its bounded artifact scope while the parent outcome remains open.
