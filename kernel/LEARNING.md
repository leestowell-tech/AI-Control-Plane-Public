# Governed learning and reusable capability

Status: PORTABLE ADAPTATION / NOT AUTONOMOUS SELF-MODIFICATION
Lineage: existing evidence, trust/admission and hypothesis responsibilities. This file adapts their semantics; it does not create another learning backend.

## Two loops
Local experience: work → evidence → candidate/current-state correction → appropriate review → adopted change → later outcome.
Shared methods: source improvement → applicability/custody/maturity review → portable release → user-instance receiving → later outcome/rollback. Use deployment/UPDATES.md.

## Capture in existing owners
Detect material success, failure, friction, repeated correction, drift, tool limits, useful research and unexpected outcomes during ordinary work. Preserve problem, source/version, context, intervention, expected/observed result, limitations and next resolving action.
Use the bound indexed memory under deployment/MEMORY_WORKFLOW.md for compact LEARNING_CANDIDATE/HYPOTHESIS records; use the actual domain/mission artifact when it owns detail and link it from current state. Do not create a duplicate database.
The existing revision details text can hold candidate status, scope, falsifier, supporting/contrary evidence, review result and next action. Structural record validation does not validate these meanings.

## Distinguish treatments
- Changed current fact/plan → current-state/domain update with provenance.
- Stated user preference/decision → attributed record of actual intent and scope.
- Reusable possible lesson/capability → LEARNING_CANDIDATE, not canon.
- Consequential unresolved causal/predictive proposition → HYPOTHESIS with what would resolve it.
- Domain-specific result → local lineage; no forced generalization.
- Insufficient evidence/no useful signal → explicit limitation or no capture.

## Trust, admission and lifecycle
For information that may influence a consequential choice, check source, currentness, scope, status, contradictions and permitted use. Admission can be authority, context, evidence, historical, candidate/hypothesis, reconciliation-required, superseded or irrelevant. Retrieval alone does not promote it.
Follow OBSERVATION → CANDIDATE → REVIEW/VALIDATE → PROMOTE/REJECT/DEFER → REVALIDATE/DEMOTE/SUPERSEDE. Preserve evidence and rationale for a status change. Resolve competing claims without hiding the contrary source.
Candidate extraction may be inferred during ordinary authorized work. Adoption that changes authority, financial/risk rules, security, external actions or governing behavior requires the current user's applicable grant; high-impact expansion requires explicit approval. A source maintainer's grant does not transfer.
User preference is not universal empirical truth; repeated assistant claims are not independent evidence. Do not copy source-owner private history into this instance.

## Demonstrate transfer
A method helping on the example that produced it is limited evidence. Where a generalized claim matters, seek a later different task, counterexample or holdout before claiming broader benefit. Record escaped defects, harmful advice, false criticism, effort and benefit. This is an evaluation lens, not a claim all generalized methods are validated.
Retrieve relevant accepted lessons and dated negative knowledge at the next actual Build/Reset/research task. Keep candidates available as uncertain context; do not make them governing rules. A saved item that cannot be found at use remains a retrieval gap.

## Maintenance and privacy
Repeated reusable work should improve its existing producer or procedure rather than become repeated conversational reminders. Under the current instance's actual policy/grant, create or update a supported skill/procedure when that trigger is met. Reuse an existing one; if the instruction still repeats, diagnose discovery, selection, loading, execution and receiving before adding another copy. Record the trigger, intended result, affected owner, check and later result in existing lineage. A source author's preferred repetition count or default trust stance is not another user's policy.

Separate procedural packaging from empirical promotion. A useful procedure can be prepared within current reversible-work authority; installing tools, changing governing behavior or exporting private data still needs the recipient's applicable authority. Apply the host's real creation/validation/persistence path and verify discoverability. A saved skill is not evidence that it was selected, loaded or beneficial.

Contradiction, drift, model/tool changes, missed retrieval or excess burden trigger bounded review under kernel/MAINTENANCE.md. Preserve current decisions and unique history; rollback a method separately from user data.
Share only consented generalized feedback across instances. No automatic export of private records, external message, ambient watcher or universal semantic promotion. The maintainer reviews affected shared methods; each user owns adoption and effect authority.
