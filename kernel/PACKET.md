# Packet — decision, execution, review and handoff

Status: PORTABLE ADAPTATION / TARGET BEHAVIOR UNOBSERVED
Trigger: Packet, prepare the packet or a clear request for a complete decision/transfer. Build uses the appropriate view for its real decision. Infer APPROVAL / EXECUTION / REVIEW / HANDOFF from verified phase and authority. No new permission follows from formatting.

## Common preparation
Recover original outcome, earlier requirements/corrections, owner sources, exact candidate/version, scope and grants/holds. Preserve completed, executable, blocked, observation, deferred and superseded work. Carry evidence limits, costs, constraints, receiving, rollback and next owner.
Before delivery ask: what would successful execution of this actual envelope still leave unfinished? Complete feasible decision-critical preparation. A parent title or list of IDs does not prove coverage. Each needed residual must be included, independently continuing, or held at a real decision/dependency/owner-approved deferral.

## Approval view
Present in this order, compactly when possible:
1. Decision and recommendation.
2. Problem, current state, supporting evidence/confidence.
3. Concrete proposed result, scope and behavior.
4. Serious alternatives and decisive research/challenge findings.
5. Risks, unknowns, resources/dependencies and rollback.
6. Implementation sequence and validation, including integration/consolidation.
7. Exact new authority requested, exclusions and real later gates.
8. Current status, next owner and what follows approval, hold or rejection.

The user must be able to decide without opening a link. Do not request conceptual approval then invent the actual candidate afterward. Use existing grants without another ceremony.
An unqualified Start/Approved/Execute to a concrete execution request means proceed in the same run under that exact scope, after necessary preflight. Testing-only/direction-only/hold qualifications prevail. A new target, cost or consequence outside the grant requires the genuine decision, not inferred permission.

## Execution, review and handoff views
EXECUTION: objective, approved envelope, target/environment/version, requirements, action order, protected boundaries, checks, evidence return, stop/recovery and next owner.
REVIEW: original requirements, exact candidate, sources, uncertainty, actual review conditions and allowed next transition. Apply kernel/CHECK.md when invoked or when the material check needs it.
HANDOFF: whole mission, branch status, bottleneck, first permitted action, authority/holds, exact destination, required source checks, negative knowledge, receipt route and remaining work. Direct authorized transfer is preferable to avoidable manual relay. If human relay is necessary, provide one complete payload and the verified destination; an internal branch/path is not a user-visible destination. Prepared is not dispatched.

## Maximum packet
For an explicit maximum packet request, recover the source objective before grading a candidate. Develop the strongest useful supported solution, a simpler/no-change comparator and a materially stronger resource-dependent option. Use effort on real decision-changing evidence and concrete candidates. Report actual tool/test/reviewer coverage; never invent independence, hidden resources, spending or exhaustive coverage.
Preserve capability when compressing. Challenge both unjustified expansion and contraction. Stop preparation when the real decision is supported or at an evidenced boundary; do not build an endless review apparatus.

## Custody
Keep one controlling record and derive the conversational view. Read back durable changes. Stale or conflicting evidence blocks affected actions, not independent work. Publication, settings, external communication and effect authority remain separately governed. A packet can be complete while implementation remains open; state both.
