## Entry inheritance and receiving
Identify the actual repository entry file(s), intended host/root/branch/cwd and local controlling record. Bind the current approved shared control-plane, assurance, behavior-selection, mission-continuity and capture/learning routes by reference; list applicability or an explicit reason for non-applicability. Record inspected revisions and conflicts in the existing receiving record. Shared research is not copied doctrine or new authority.

Creation is not complete because an entry file exists. Use the user instance's current entry template/validator; verify generated bindings, resolved sources and local authority, then read back the published receiver. Test the actual host instruction chain, including overrides, filename rules, context limits and active branch; keep SOURCE_RECEIVED, HOST_LOADING and ordinary effectiveness distinct. A future shared change must reach both the entry producer/template and affected existing consumers. Use existing source reconciliation/receiving, not a new registry or scheduler. When access fails, preserve the specific gap and continue independent work.

This is conditional on a material inherited claim, not a mandatory historical audit or a second authority store.
